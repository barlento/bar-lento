Live site: **https://bar-lento.vercel.app** (Vercel project `bar-lento`, team "BAR LENTO", auto-deploys from `main`, ~60–90 s).
Owner: Bar Lento, 158 8th Avenue, New York (info@barlentony.com). Floor manager: **Marta** (not technical — she edits from the site, never from code).
The owner writes in Italian; answer him in Italian. Everything staff sees on the site is in **English** (the team is mixed Italian/American). The IT/EN toggle exists only inside manager mode and must translate EVERYTHING the manager sees (header, hero, tabs, day/month names, cards, time clock, ranking, personal panels): use `t()`/`data-t` and the `L_EN`/`L_IT` day-month tables for any new text. ## How to publish a change (the only job that needs code)
Edit the files, commit, `git push origin main`. That's it — Vercel builds and publishes automatically. No build step, no npm install locally (Vercel installs `web-push`).
Push directly to `main` (no PR needed) unless the owner asks otherwise. If a direct push is refused, push a branch and tell the owner to tap **Create PR → Merge**.
Verify after ~90 s at https://bar-lento.vercel.app (add `?v=<n>` to bypass caches). `*.vercel.app` may be unreachable from the sandbox network — say so instead of guessing.

## Architecture (vanilla, no framework)
- `index.html` — the whole UI (staff + manager) in one file: CSS, i18n dict `I18N.en/it` (`t()`, `data-t`), IIFE app. Polls `/api/data` every 30 s while visible. Service worker `sw.js` (push display only, no caching). PWA: `manifest.webmanifest`, `icons/`.
- `api/*.js` — Vercel serverless functions (Node, CommonJS):
  `data` (GET schedule / POST save with optimistic `version`, 409 on conflict; removing a staff name also wipes their PIN + devices), `login` (returns the role), `confirm`, `log`, `export` (Excel workbooks: schedule archive, personnel record), `push` (subscriptions, tied to the signed-in person), `toast` (POS: `status`, `today`, `clock`, `employees`, `who`), `me` (personal access: `begin`/`create`/`login`/`logout`, `who`, `hours&week=` per-person Toast entries, manager `list`/`reset`, app clock `punch`/`punches`).
- `lib/store.js` — Upstash Redis via REST (env prefix auto-detected KV_/UPSTASH_REDIS_/STORAGE_/REDIS_); seed fallback `data.json`. Keys: `barlento:schedule`, `barlento:confirm`, `barlento:log`, `barlento:pending*`, `barlento:announce`, `barlento:push`, `barlento:toast:*`, `barlento:pin` (name → scrypt hash), `barlento:sessions` (device token → name), `barlento:rules_ack` / `barlento:rules_ack_archive` (House Rules acknowledgments, legal record).
- `lib/accounts.js` — staff PIN accounts: 4 digits, scrypt+salt, 5 wrong tries → growing lock (5→60 min), random 48-hex device token in header `x-staff-token` (localStorage `bl_me_token`/`bl_me_name`), `resetPin` = clear PIN + sign out everywhere.
- `lib/diff.js` — computes changes between saves → history log + "notable" changes for the batched push.
- `lib/push.js` — Web Push (VAPID; public key in file, private in env `VAPID_PRIVATE_KEY`), `flushPending` with quiet hours.
- `lib/mail.js` — outgoing email for the signed copy of the House Rules: SMTP via nodemailer (`SMTP_HOST/PORT/USER/PASS`, e.g. Google Workspace app password) or Resend (`RESEND_API_KEY`), `MAIL_FROM` optional, `MAIL_WEBHOOK_URL` for local tests. `enabled()` → `features.mail`. **LIVE via Resend** since 2026-09-18: `RESEND_API_KEY` + `MAIL_FROM` on Vercel, domain barlentony.com verified (DKIM TXT `resend._domainkey` + CNAME `rsend`/`send` on Squarespace DNS; Google MX/SPF/DKIM untouched, receiving stays OFF). If not configured the acknowledgment is still recorded; Marta can re-send later with the ✉ button in Staff.
- `lib/toast.js` — Toast POS Standard API (read-only): login, restaurant auto-discovery, employees (paginated), time entries, `dayStatus`, `autoMap` (fuzzy first-name matching so nobody maps names by hand). Env: `TOAST_CLIENT_ID`, `TOAST_CLIENT_SECRET` (optional `TOAST_RESTAURANT_GUID`).
- `documents.js` — staff policies (see 📂 Documents below), `docs.html` printable versions.
- `lib/former.js` — register of people no longer on staff (`barlento:former`: name, Toast guid, full name, email, removedAt, by manager/toast), written by both removal paths, never deleted; manager `list` returns `formerStaff`. **Reports are proof of ACTUAL work (owner's rule 2026-09-19)**: every report is built from clock-ins (Toast POS or app); the published schedule is a plan and is never presented as hours worked (manager report lists it after the clock-ins under "Scheduled shifts (the plan, not proof of work)"). Nothing about money or tips, ever. **Employee's own report** (`GET /api/export?mine=1&from&to`, `x-staff-token`, default = current schedule week, max 12 months; My week → **Week report** button = the week shown): hours worked, clock-ins, days worked, every clock-in with exact times and "Recorded by", totals by day, a plain-language note — no schedule, no documents, no manager fields. **Sunday-night email** (`api/weekly.js`, Vercel cron `0 4 * * 1` UTC = Sunday 23:00 EST / midnight EDT; manager can rerun with `?week=<Monday>&force=1` + password; one send per week via `barlento:weekly_sent:<week>`; cron auth = `CRON_SECRET` bearer if set, else Vercel's cron headers): every person on staff with clock-ins that week gets "Your Bar Lento week — …" with hours worked and their PDF attached (email = the one they signed with, else Toast email; test accounts and people without email or without clock-ins are skipped), plus ONE summary email to `copyTo` listing sent/skipped/failed, and a history line. `lib/mail.send` accepts `attachments`. **Personnel record (manager)**: `GET /api/export?person=Name[&from&to]` (password) → an official **PDF** by default (`lib/pdf.js` on `pdfkit`, US Letter, Helvetica, Apple-like: kicker + title, five number tiles, key/values, month-by-month, then Shifts / Clock-ins / Documents / Staff events tables with repeated headers, Certification paragraph citing NY Labor Law §195(4), §661, 12 NYCRR §146-2.1, NYC Admin Code §20-919, Labor Law §201-g; footer on every page with generation time, page x of y and the report's SHA-256 fingerprint; PDF permissions: printing allowed, editing disabled). `&format=xlsx` gives the Excel workbook instead (`exceljs`): sheets **Summary** (identity, status, period, totals, month-by-month table), **Shifts**, **Clock-ins** (Toast POS + app, source column, fetched month by month by guid, works for archived employees), **Documents** (every signed policy incl. older versions/archives: version, email, device, SHA-256), **Events** (staff changes, exact-name match). Bold grey headers, frozen header row, autofilter, real date cells, hours as numbers, print footer. `GET /api/export` (no person) = schedule archive, PDF by default (one table per week, day notes inline) or `&format=xlsx` (Summary, Shifts, Days). Default period 12 months, max 24. Buttons: person sheet "Download PDF", the **Former staff** list at the bottom of Staff, and the manager bar "Export PDF". Preview PDFs locally with `node tools/pdfshot.js file.pdf out/prefix` (pdf.js in headless Chromium). Nothing is ever deleted on removal: past shifts stay in `weeks`, acks → archives, punches → archive, Toast link → former register.
- `lib/backfill.js` — **History before the launch from Toast** (one-time, days ≤ `HISTORY_UNTIL` 2026-09-18; the devserver sets `BACKFILL_UNTIL=2099-12-31` so the suites still exercise it): `backfillFromToast(doc, from)` reads every closed Toast clock-in from `from` (whole weeks) to last Sunday (`toast.timeEntriesSpan`, 28-day chunks), maps guid → name (explicit links, safe fuzzy matches, then the former register so archived employees still land under their name), and rewrites every past week in that range: only real clock-ins remain — Toast people from Toast (`src:"toast"`, id `t-<toast guid>`), app-clock people from their app clock-ins incl. archived ones (`src:"app"`, id `a-<in>`), both kept by `normalizeShift` — every planned shift replaced (+ archived to `barlento:plan_archive`), days after `HISTORY_UNTIL` never touched (they are Marta's plan, even once they are in the past); weeks are created when missing; confirmations pruned; one history line "Past weeks from Toast: N clock-ins (first to last), k new, r planned shifts replaced, w new weeks". Idempotent. **Runs by itself**: `backfill.auto(doc, doc0.updatedAt)` on every GET `/api/data` (last 8 weeks, at most once per 6 h via `barlento:backfill_at:v2` (bump the suffix when the rule changes), never within 90 s of a manager save, never throws). The manager button in Staff ("Import past clock-ins from Toast", `POST /api/data {action:"backfillToast"[, from]}`, default 12 months) does the same over the long range and shows the numbers ("Past weeks updated: N clock-ins from Toast (date to date), w weeks changed, r planned shifts replaced" / "already match" / "Toast has no clock-ins between …"). In reports they are never listed as "Scheduled shifts" (the clock-ins are the proof). In the app such shifts show a "Toast"/"App" tag instead of a station. Marta is salaried (hired 2026-08-17, Mon–Fri for now, 5 days a week, weekends from late September) and clocks in ONLY from the app, never on the Toast terminal: a one-time migration in `api/data.js` (`barlento:migr:2026-09-19-marta-app`) put her in `appClock` so her stray Toast entries are ignored; her days come from her app clock-ins (never invent times). **Her pre-launch days were entered once with the owner's approval (2026-09-19)**: `migrationMartaDays` in `api/data.js` (flag `barlento:migr:2026-09-19-marta-days`) wrote 25 app clock entries in `barlento:punch:Marta`, Mon–Thu 3:30–10:00 PM, Fri 3:30–11:00 PM, 2026-08-17 → 2026-09-18, marked `manual:true, by:"owner"` (reports say "Entered by the owner"), and reset the history key so they land in the past weeks as `src:"app"`.
- `lib/staffsync.js` — **Staff follows Toast** (owner's request 2026-09-19): on every GET `/api/data` (max once per 10 min, never within 90 s of a manager save) every active Toast employee not yet linked becomes a person in `staff` (first name; "First L." if taken; exact `toastMap` link so the Toast email prefills the signature), log line "Added from Toast: …", the manager sees a toast and the Staff lead says so; two Toast records with the same first name as an unlinked existing person → the older `createdDate` is the existing one; archived (`deleted`) employees are skipped. Removing a person puts their guid in `toastIgnore` (server-side in `api/data` POST) so they never come back. **Archived in Toast → removed from the app automatically** (owner's rule 2026-09-19): on the same sync, any staff name with an explicit `toastMap` link to an employee whose record is archived (`deleted`, or a real `deletedDate`; Toast writes `1970-01-01` for "never") is removed like the manager's Remove (upcoming shifts deleted, past weeks untouched, PIN/devices closed, signatures and clock-ins archived, log line "Removed from staff (archived in Toast)"), NOT added to `toastIgnore` (re-activated in Toast → comes back); a guid missing from Toast's answer never removes anyone. People added by hand (no link) are managed only in the app. Toast test accounts (`Test …`) are never added. Opening Staff (manager `list`) syncs right now with a fresh employee list (`force`), the roster shows a grey line "Toast: N active employees · Not in the app: X (removed here / waiting)" (`toastReport`) so nobody wonders why someone is missing. Person sheet shows "Toast · Full name · email" (manager `list` returns `toast`). Nobody types names or emails twice.
- `lib/presence.js` — **Who is online (manager only, owner's request 2026-09-19)**: every call from a signed-in device (the 45 s poll of `/api/data` and any `/api/me` call with a valid `x-staff-token`) writes name → last seen in `barlento:presence`; manager `list` returns `presence{name:{lastSeen, online}}` (online = seen in the last 90 s; `lastSeen` falls back to the newest `lastSeen` of the person's PIN sessions, `accounts.summary`, so people who used the app before presence existed still show a date). Staff roster: a pulsing green dot on the avatar + "Online now" when the app is open on their phone, a soft red dot + "Last seen 5 min ago" / "Not seen yet" otherwise, a header line "3 of 12 online now"; the roster refreshes every 15 s while open. Staff never see it. **Live everywhere (owner's request 2026-09-19)**: the app polls `/api/data` + today's clock-ins every 30 s while visible, the Time clock every 30 s, Toast time entries are cached 30 s.
